## 1. Goal

Make a running HAOS VM on Proxmox (already in use, fitted out with devices/integrations,
using HACS) easy to maintain and family-friendly:

1. **Version everything** — full git history of the HA configuration, system-level VM
   backups, and runtime backups on three independent layers.
2. **A resident chat agent** that family can talk to (text) to read and change schedules.
3. **Human-readable summaries** of all active automations and schedules, in plain text.
4. **Clean up the rotted build** — stale add-ons, abandoned HACS integrations, dead
   devices/entities/automations.
5. **Restore order/prettiness** — sane config structure, a family dashboard, docs.

---

## 2. Two different "agents"

- **Build agent** (opencode, working from this machine + SSH into HA): does the versioning,
  cleanup, config refactor, and ongoing maintenance.
- **Resident chat agent** (Home Assistant **Assist** conversation agent): a permanent
  feature on the HA app. Gets live access to all entity states and can change schedule
  helpers. This is who the family chats with.

---

## 3. Versioning strategy (three independent layers)

| Layer | Mechanism | Purpose |
|-------|-----------|---------|
| 1. Config-as-code | **Git Exporter add-on** (Poeschl) pushes `/config` to a **private GitHub repo** on an interval (~30–60 min). Exports dashboards (Lovelace from `.storage`) and add-on configs; built-in plaintext-secrets check. | Diff + rollback of every change, including UI-driven ones. |
| 2. VM snapshots | Proxmox `vzdump` of the HAOS VM with retention (e.g. daily ×14, weekly ×4, monthly ×2). | "Undo" a bad HAOS/OS update; full VM restore. Crib sheet in `proxmox/` (config-only, agent does not manage Proxmox). |
| 3. Runtime state | Home Assistant built-in backups; Proxmox layer above. | Recovers `.storage`, DB, secrets — the parts git must not hold. |

**Excluded from git:** `.storage/`, `home-assistant_v2.db`, `secrets.yaml`, SSH keys, caches.
The exporter's secrets check is a safety net, not the primary control.

---

## 4. Config style: hybrid

- **UI-driven** for device/integration setup (sign-ins, add devices). Lives in `.storage`,
  auto-exported by Git Exporter.
- **YAML** for everything agent/family-facing: automations, scripts, scenes, and schedules.

**Schedules as YAML-defined helpers** (`config/input_datetime/schedules.yaml` etc.):

```yaml
# input_datetime/schedules.yaml
heating_morning_weekday:
  name: "Heating: weekday morning"
  has_date: false
  has_time: true
  icon: mdi:radiator
  initial: "06:30"
```

Family edits these **either** via a curated Lovelace dashboard **or** by chatting with the
resident agent — both write the same helpers, so they never race. Every change is a commit.

## 5. Family chat agent (Part B)

- **Model provider: OpenRouter, to start** (user's preference): built-in OpenAI-compatible
  conversation integration with `base_url: https://openrouter.ai/api/v1`, a capability-rated
  chat model, API key stored in `secrets.yaml` (never committed).
- **Optional later:** switch to **Ollama** (add-on in HAOS or a clean LXC on Proxmox with a
  7–14B function-calling model) for full offline/privacy. Switching is a config change, not a rework.
- **Interaction:** text chat only (no voice yet).
- **Persona / system prompt:** "You are the family's home assistant scheduler. Explain
  current schedules simply, propose changes, and update them when asked." Written by the
  build agent, versioned in the repo.
- **Data access + guardrails:** Assist hands the LLM live entity states; exposed devices are
  **scoped to schedule helpers + automations only** so the agent can only touch scheduling —
  not cameras, doors, or alarms. This scope is also the privacy control for OpenRouter.
- **Mechanics:** the chat agent changes schedule helpers via normal HA service calls; existing
  automations simply follow the helper values.

## 6. Plain-text summaries (Part C)

- `docs/SCHEDULES.md` — every schedule in plain language + what it controls.
- `docs/AUTOMATIONS.md` — every automation: purpose, state (on/off/disabled), dependencies.
- Generated by `tools/summarize.py` (parses automations + `input_*` YAML); the build agent
  runs it and **commits on every config change** so docs never drift from reality.
  (Later option: run it as a GitHub Action.)
- The chat agent can reference these (via persona + a summary helper entity), so family can
  also just ask "what happens at 18:00?".

## 7. Build cleanup (Part D) — Balanced

Live family home, so: report first, stage changes, disable rather than delete, your sign-off
on ambiguous items. All reversible via the git history layer established first.

1. **Inventory breaking change:** dump installed add-ons, HACS repos, entity/device
   registries, all automations/scripts → `docs/inventory.md`.
2. **HACS audit** (biggest rot source): check each custom integration for archived /
   unmaintained repos (GitHub API repo-status check); classify *keep / replace / remove*.
3. **Add-on audit:** `ha addons list`; flag stale/abandoned add-ons; remove or pin with
   justification.
4. **Dead entities/devices:** prune registry entries whose integrations are gone or never
   appear; **disable** (not delete) ambiguous ones; enable recorder's `exclude_missing_entities`
   to auto-drop gone entities and shrink the DB.
5. **Automation/script sweep:** duplicates, broken references, long-disabled rules → move to
   `config/deprecated/` (kept in git history) rather than delete.
6. **Config hygiene:** deprecated keys, commented-out blocks, stale includes.
7. `docs/cleanup_report.md` — removed / replaced / needs-your-OK with reasons; each step in a
   separate commit.

## 11. P1 checklist — versioned config via Git Exporter

The add-on is **push-only from `/config`**, but with `repository.pull_before_push: true`
(default) it pulls newer remote commits into `/config` first — so changes we commit to the
GitHub repo **do** flow into the VM on the next sync. That's the channel the build agent
uses to ship config to HA.

Steps for the user:

1. GitHub → **New repository** → name `ha_config`, **Private** (no README/.gitignore — set up in git already). Leave it empty except what the exporter pushes.
2. GitHub → Settings → Developer settings → **Personal access tokens → Fine-grained** → *Generate new token*: Repository access → **Only select** → `ha_config`; Permissions → **Repository permissions → Contents: Read and write** → generate. (The token only ever lives inside the HA add-on.)
3. HA → Settings → Add-ons → **⋮ → Repositories** → add `https://github.com/Poeschl-HomeAssistant-Addons/repository` → install **Home Assistant Git Exporter**.
4. Configure (matches the add-on options schema):

   - `repository.url` → `https://github.com/<you>/ha_config`
   - `repository.username` → your GitHub username
   - `repository.password` → paste the fine-grained PAT
   - `repository.branch_name` → `main`
   - `pull_before_push` → ON (default)
   - `export.lovelace / addons` → ON; `esphome / node_red` → OFF (not used)
   - `check.check_for_secrets` → ON (default, safety net)
   - **Extend `exclude`** with: `.storage/`, `secrets.yaml`, `.ssh/`, `.cloud/`
     (defaults already skip `*.db`, `*.log*`, `__pycache__`, `tts/`, `deps/`)
   - Logging → **show in sidebar: ON** (handy monitoring)

5. **Start** the add-on. It imports current `/config` → GitHub (first push ~1 min).
6. Confirm: repo root now contains `configuration.yaml`, `automations.yaml`, `groups.yaml`, `custom_components/` etc., and **no** `.storage`, `secrets.yaml`, or `*.db`.

Afterwards I sync this local workspace to the repo (`git fetch`/reset to `origin/main`)
and start P3/P4 with versioning in place.

## 10. Risks & tradeoffs

- **OpenRouter** sends entity names/states to a third party. Mitigated by exposing only
  scheduling entities; full-local Ollama is a config change away.
- **Cleanup on a live home** may briefly affect family automations. Mitigated by versioning,
  staged disable-not-delete, and sign-off on ambiguity.
- **LLM quality varies** by model. OpenRouter model is strong; local models are decent but
  clumsier at multi-step edits. Persona restricts it to scheduling to bound mistakes.
- **HACS + HA upgrades** can break custom integrations; unmaintained ones get removed or
  replaced during the cleanup.
